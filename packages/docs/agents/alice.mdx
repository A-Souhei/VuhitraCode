Alice is a pure orchestrator agent that plans, delegates, and verifies work without implementing anything itself. She dispatches up to 7 Sentinel or Scout workers to execute independent tasks concurrently and verifies completion before declaring done.

## Overview

Alice excels at:

- **Planning** - Breaking down complex tasks into atomic, independently verifiable items
- **Delegating** - Spawning up to 7 parallel Sentinel or Scout workers to execute tasks
- **Orchestrating** - Managing dependencies and coordinating work across multiple agents
- **Verifying** - Using Keeper agents to validate work completion before proceeding

Alice follows a strict 6-phase workflow (with Phase 4b as a sub-phase) ensuring structured execution:

1. **Phase 0** - Silent mode intake (optional preferences)
2. **Phase 1** - Gather context via explore agents
3. **Phase 2** - Create TODO list
4. **Phase 3** - Execute in parallel (up to 7 Sentinels or Scouts)
5. **Phase 4** - Keeper verification
6. **Phase 4b** - Code review (inline with Inspect agents)
7. **Phase 5** - Testing
8. **Phase 6** - Commit and push

### Silent Mode Configuration

In silent mode, Alice collects preferences for:

- **Time limit** - Maximum execution time before stopping
- **Audit** - Whether to run code review
- **Audit focus areas** - Security, Performance, Logic, Style, Tests, Docs
- **Auto-fix findings** - Apply audit findings automatically
- **Review rounds** - Max iterations for fix/re-verify cycles
- **Tests** - Integrity+Unit, Integrity only, Unit only, or skip
- **Commit** - No commit, current branch, or new branch
- **Push** - Whether to push to remote after commit

## Parallel Execution

Alice leverages parallel processing throughout:

- **Up to 3 parallel explores** for codebase mapping
- **Up to 7 parallel Sentinels or Scouts** for task execution (combined total)
- **Up to 7 parallel Inspect agents** for code review
- **Up to 3 concurrent test agents** for verification

Alice uses two types of workers for task execution:

- **Sentinels** for complex tasks — multi-file changes, refactors, tasks requiring exploration
- **Scouts** for simple tasks — single file edits, small targeted changes, renames

This enables Alice to handle large, complex projects efficiently while optimizing costs for simpler work.

## Phase-by-Phase Workflow

### Phase 0: Silent Mode Intake

Alice optionally asks if you want to run in silent mode. If yes, she collects all preferences upfront. If no, she proceeds to interactive mode.

### Phase 1: Gather Context

Before touching files, Alice may call explore subagents to map relevant code areas. For trivially scoped changes, this step is skipped.

- Single explore for focused changes
- Up to 3 explores for broad changes

### Phase 2: Create TODO List

Alice creates a complete, ordered TODO list with atomic items before any implementation begins.

### Phase 3: Execute (Parallel)

Alice spawns up to 7 Sentinels or Scouts to execute independent TODO items in parallel:

1. Mark batch items as `in_progress`
2. Spawn workers with full context
3. Wait for all to complete
4. Mark completed items
5. Repeat with next batch

**Critical rule**: Alice never implements tasks herself — every item is delegated to a Sentinel or Scout.

#### Scout vs Sentinel — Choosing the Right Worker

Alice chooses the appropriate worker type based on task complexity:

**Dispatch a Scout for:**

- Simple single-file edits
- Small targeted changes
- Self-contained tasks
- Tasks estimated to complete in a few steps

**Dispatch a Sentinel for:**

- Multi-file changes
- Complex logic or refactors
- Tasks with unknowns or exploration needed
- Cross-cutting concerns

**When in doubt, use Sentinel.**

Scout runs on a cheaper, faster model (configured by the user) and is nearly identical to Sentinel — same write/edit/bash access, same reporting format — except Scout cannot spawn sub-agents.

### Phase 4: Keeper Verification

After all items complete, Alice calls a Keeper agent to verify the work:

- If incomplete: re-open items and dispatch new Sentinels
- If `ALL CLEAR`: proceed to Phase 4b

### Phase 4b: Code Review (Inline)

In silent mode: check `audit` config; if `no`, skip to Phase 5; if `yes`, run inline review.

In interactive mode: ask the user about review.

If reviewing:

1. Determine focus areas (security, performance, logic, style, tests, docs)
2. Build review plan for modified files
3. Dispatch Inspect agents (up to 7 in parallel)
4. Collect findings and present to user
5. If auto-fixing: dispatch Sentinels to apply findings, then re-verify with Keeper
6. Track review rounds (cap at `REVIEW_MAX_ROUNDS`)

### Phase 5: Testing

Based on preferences, run:

- **Integrity + Unit** - Full verification (recommended)
- **Integrity only** - Lint, type-check, build
- **Unit only** - Unit tests only
- **Skip** - No testing

### Phase 6: Commit and Push

Based on preferences:

- **No commit** - Stop here
- **Current branch** - Commit all changes on current branch
- **New branch** - Create new branch and commit
- After commit: optionally push to remote

## Bridge Mode

When Bridge Mode is active, Alice on the master instance can dispatch tasks to connected friend nodes as additional workers. This enables distributed task execution across multiple machines.

### Dispatching Tasks to Friends

Alice dispatches tasks to friend nodes using the **`[bridge_node: nodeID]`** tag at the **START** of any Task tool prompt:

```
[bridge_node: friend-node-abc123]
Refactor the payment module to support Stripe webhooks.
```

When Alice includes this tag:

1. **Blocking dispatch** — The Task tool POSTs the work to the friend node and then blocks (polling Redis every 2 seconds)
2. **Synchronous result** — The friend's result is returned inline within up to 5 minutes; it does NOT appear later in shared context
3. **Worker selection** — Only **`scout`** and **`sentinel`** subagents may be dispatched to friends; **`explore` is strictly forbidden** for bridge dispatch (explore is only for Alice's own local codebase exploration)

### Checking Friend Health

Alice can call the **`ping_bridge_session`** tool (only available when Bridge Mode is active) to verify a friend node is still alive before dispatching work:

```ts
ping_bridge_session({ nodeID: "friend-node-abc123" })
// Returns: true if heartbeat received within last 60 seconds (sent every 15 seconds)
// Returns: false if no recent heartbeat
```

### When to Dispatch to Friends

- **Dispatch to a friend** when the task clearly concerns the friend's directory/codebase
- **Handle locally** if the task is about Alice's own directory
- **If ambiguous**, dispatch to the friend and note what you're doing

### Launching Alice in Bridge Mode

```bash
# Master (Alice orchestrates here)
opencode --bridge master --coordinator redis://host:6379

# Friend (requires --bridge-id flag pointing to master's session ID)
opencode --bridge friend --bridge-id <master-session-id> --coordinator redis://host:6379
```

Friend terminals show `⚡friend` in the prompt bar; Master Alice shows `⚡master`.

See [Bridge Mode](/bridge) for full setup instructions.
